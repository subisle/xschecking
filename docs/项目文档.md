下面我给你的是一份**可以直接作为「后端总设计文档（V1.0）」的完整文档**，目标只有一个：
**先把后端“骨架”搭到位，保证后续卡密、一机一码、云函数、防破解都能无痛扩展。**

技术栈以 **Go（Gin）** 为核心，设计思路对标 **Google 的认证模型 + 授权软件场景**，但**不追求轻量，而追求可控与安全**。

---

# 授权网站后端基础框架设计文档（V1.0）

## 1. 项目目标与边界

### 1.1 项目目标

* 提供一个 **授权 / 登录 / 注册 / 校验型后端服务**
* 所有用户行为必须：

  * 可追踪
  * 可风控
  * 可失效
* 前端仅作为 **管理与展示**
* 实际授权逻辑以后端为准

### 1.2 明确不做的事情（当前阶段）

* ❌ OAuth / 第三方登录
* ❌ 社交绑定
* ❌ 无验证码登录
* ❌ 客户端完全信任

---

## 2. 技术栈与基础组件

### 2.1 技术选型

| 层级     | 技术                   |
| ------ | -------------------- |
| Web 框架 | Gin                  |
| 配置     | Viper                |

## 3. 后端总体架构

```
cmd/
 └─ server/
    └─ main.go

internal/
 ├─ config/        # 配置加载
 ├─ router/        # 路由注册
 ├─ middleware/    # 中间件
 ├─ handler/       # HTTP 控制层
 ├─ service/       # 业务逻辑层
 ├─ repository/    # 数据访问层
 ├─ model/         # 数据模型
 ├─ pkg/           # 公共工具
 ├─ risk/          # 风控模块
 └─ auth/          # 认证与会话
```

---

## 4. 核心模块拆分（必须先实现）

### 4.1 配置模块（config）

职责：

* 加载数据库、Redis、JWT、验证码配置
* 区分 dev / prod

关键点：

* 所有密钥 **只存在服务端**
* 验证码、邮箱、JWT key 不可硬编码

---

### 4.2 路由模块（router）

路由按「**业务域**」划分，而不是按 URL 层级。

```
/api/v1
 ├─ captcha/
 ├─ auth/
 ├─ user/
 ├─ email/
 ├─ admin/
```

---

### 4.3 中间件模块（middleware）

#### 必须具备的中间件

| 中间件       | 作用     |
| --------- | ------ |
| RequestID | 请求追踪   |
| Logger    | 访问日志   |
| Recovery  | 崩溃保护   |
| RateLimit | 防刷     |
| Auth      | JWT 校验 |
| Risk      | 风控拦截   |

---

## 5. 验证码与一次性凭证模块（核心）

### 5.1 验证码模块（captcha）

职责：

* 对接 LuckyCola
* 生成验证码
* 校验验证码

**验证码不直接授权业务，只生成通行证**

---

### 5.2 captcha_pass_token 机制（必须）

#### 设计目的

* 防重放
* 防接口跳过
* 防脚本串联调用

#### 数据结构

```sql
captcha_token
- token
- captcha_id
- ip
- ua_hash
- used
- expire_at
```

#### 使用规则

* 校验成功生成
* 一次性使用
* 成功 / 失败都销毁

---

## 6. 用户模块（User）

### 6.1 用户状态模型

```text
未注册
 → 已注册
   → 正常
   → 冻结
   → 封禁
```

### 6.2 用户表核心字段

```sql
user
- id
- email
- password_hash
- status
- created_at
- last_login_at
```

---

## 7. 注册流程（后端逻辑）

### 顺序不可更改

1. 校验 captcha_pass_token
2. 校验邮箱验证码
3. 校验卡密
4. 风控判断
5. 创建用户

**任何失败 → token、验证码全部作废**

---

## 8. 登录模块（Auth）

### 8.1 登录流程

```
验证码
 → captcha_pass_token
 → 登录接口
 → JWT
```

### 8.2 登录风控（基础版）

| 维度 | 规则     |
| -- | ------ |
| IP | 失败次数限制 |
| 账号 | 连续失败冻结 |
| UA | 异常标记   |

---

## 9. 邮箱验证码模块（Email）

### 9.1 设计原则

* 必须绑定操作类型（注册 / 登录 / 重置）
* 不允许通用验证码

### 9.2 校验规则

| 项目   | 规则    |
| ---- | ----- |
| 有效期  | 5 分钟  |
| 错误次数 | 3 次失效 |
| 使用次数 | 1 次   |

---

## 10. 会话系统（JWT）

### 10.1 JWT 内容

```json
{
  uid,
  login_at,
  ip_segment,
  ua_hash
}
```

### 10.2 会话校验

* IP / UA 变化 → 强制重新登录
* 高频访问 → 风控拦截

---

## 11. 风控模块（Risk）

### 当前阶段做什么

* 登录失败计数
* 注册频率控制
* 邮箱验证码频控

### 为后续预留

* 行为评分
* 设备指纹
* 一机一码

---

## 12. 管理后台（Admin）

### 特点

* 必须验证码
* 不允许弱密码
* 所有操作审计

---

## 13. 推荐后端实现顺序（非常重要）

**按这个顺序，100%不返工：**

1. 项目骨架 + 配置
2. 验证码 + captcha_token
3. 邮箱验证码
4. 用户注册
5. 用户登录
6. JWT 会话
7. 风控模块
8. 卡密
9. 一机一码

---

## 14. 文档结论

这套后端框架的特点是：

* **不是“接口驱动”**
* 而是 **“安全流程驱动”**
* 每一步都为“防破解”服务
* 非一次性项目，可长期演进
